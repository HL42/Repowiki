## 二、文档导入管线（Ingest Pipeline）

### 2.1 总体流程

```
用户上传文件/指定目录
        │
        ▼
  IngestAll(dirPath)
        │
        ├─ filepath.Walk 扫描文件（支持 .md .go .py .js .ts .vue .java .rs）
        ├─ 跳过 node_modules, vendor, .git 等目录
        │
        ├─ 3 并发 goroutine 并行处理
        │
        ▼
  ingestOne(filePath)
        │
        ├─ 计算 SHA256 哈希
        ├─ 对比已存档哈希
        │
        ├─ [新文件] ──→ ingestOneNew()       ← 首次导入
        │                  │
        │                  ├─ ArchiveRaw()    归档到 raw/
        │                  ├─ SaveHash()      保存哈希
        │                  ├─ ExtractMetadata() LLM 取标题/摘要/标签/分类
        │                  ├─ generateSourcePage() 生成源摘要页
        │                  │
        │                  ├─ [规范类/引导类文档] → 跳过实体提取
        │                  └─ [普通文档] → ExtractList() 取实体/概念
        │                                  → accumulateEntityPage()
        │                                  → accumulateConceptPage()
        │
        ├─ [已修改] ──→ ingestOneUpdate()     ← 更新已有文档
        │                  │
        │                  ├─ SaveHistoryRaw() 保存旧版快照
        │                  ├─ 覆盖 raw/ 和哈希
        │                  ├─ 提取新版元数据
        │                  ├─ 提取旧版实体/概念列表
        │                  ├─ Diff 合并：新增的不删，删掉的保留
        │                  ├─ AccumulateEntityPageDiff() LLM 合并
        │                  └─ markSynthesesStale() 标记综合页过期
        │
        └─ [未变化] ──→ 跳过，打印提示
```

### 2.2 代码文件导入管线（含自动分类）

代码文件 (.go .py .js .ts .vue .java .rs) 走专属管线，包含路径规则分类：

```
ingestOneCode(rawPath, content, language)
    │
    ├─ classifyCodeFile()    ★ 路径规则分类（不用 LLM）
    │    ├─ layer:  目录路径 → handler/service/model/repository/sdk/callback/...
    │    ├─ domain: 路径关键词 → 订单/配送/门店/骑手/电商平台A/物流平台B/...
    │    └─ kind:   层级映射 → API入口/业务逻辑/数据模型/外部平台适配/...
    │
    ├─ isNoiseCodeFile()     ★ 跳过测试/mock/生成/样式文件
    │
    ├─ ChunkCodeFile()      按函数/类型/类定义边界分块
    ├─ ExtractCodeMeta()    LLM 生成模块说明（分类信息作为上下文传入）
    ├─ generateCodeSourcePage()  生成带 frontmatter 分类字段 + 代码片段的源页面
    ├─ saveCodeSourcePage()      写入 wiki/sources/code-{模块名}.md
    └─ indexSourcePage()         索引到搜索引擎
```

分类规则表见 [第十二章：代码分类系统](#十二代码分类系统-classifygo)。

导入完成后，`generateCodeAggregatePages()` 自动扫描所有 code 页面，按 domain + layer 分组，生成 `syntheses/代码模块索引.md` 聚合页。

**导入自动跳过文件：**

| 类型 | 模式 | 原因 |
|---|---|---|
| 测试文件 | `*_test.go`, `*.spec.ts`, `*.test.js` | 不含业务知识 |
| 生成代码 | `*.pb.go`, `*.pb.gw.go`, `*.gen.go` | protobuf 等自动生成 |
| Mock | `mock/`, `mocks/`, `*_mock.*`, `mock_*` | 测试辅助 |
| 样式文件 | `*.css`, `*.scss`, `*.less` | 纯样式无业务逻辑 |
| 噪声目录 | `node_modules`, `vendor`, `.git`, `dist`, `build`, `__snapshots__`, `fixtures`, `testdata` | 与代码逻辑无关 |

注意：代码导入**不提取实体/概念**，避免产生巨量无意义实体页。

### 2.3 文档更新检测

```
hash = SHA256(文件内容)
if 旧哈希存在 && 旧哈希 == 新哈希:
    跳过（内容未变）
elif 旧哈希存在:
    走更新流程（快照历史 → diff 合并）
else:
    走新导入流程
```

历史快照保存在 `wiki/history/raw/` 和 `wiki/history/sources/`，文件名格式：`{原文件名}_{时间戳}.md`。

### 2.4 跳过实体提取的文档类型

以下类型只生成源摘要页，不拆实体/概念（`shouldSkipEntityConcept` 函数）：

- **仅跳过**：SOP 流程文档（路径含 `/sop` 或以 `sop.md` 结尾）

**重要变更说明（2026-06-05 修复）：**

早期版本对 `guide`、`technical`、`report`、`meeting` 类文档也全部跳过实体/概念提取。但实际发现规范类文档（如编码规范、数据库设计规范、Git工作流）中包含大量有价值的概念（"分支管理"、"读写分离"、"事务处理"、"PR模板"），应当提取。

修复后：
- **之前**：通用项目 39 个规范文档 → entities=0, concepts=0
- **之后**：同一批文档 → entities=382, concepts=534

```go
// 当前实现 (ingest.go)
func shouldSkipEntityConcept(rawPath, category string) bool {
    lower := strings.ToLower(rawPath)
    // 仅跳过纯流程文档（SOP），这类文档以步骤为主，概念密度低
    if strings.Contains(lower, "/sop") || strings.HasSuffix(lower, "sop.md") {
        return true
    }
    return false  // 其他所有类型都允许提取实体/概念
}
```

## 三、子项目系统（Sub-Project System）

### 3.1 设计动机

我的项目等大型项目由多个独立仓库/服务组成：

| 子项目 | 源文档数 | 技术栈 | 职责 |
|--------|---------|--------|------|
| my-api | 407 | Node.js/Koa | 后端管理API |
| my-service | 254 | uni-app/Vue | APP端 |
| my-worker | 73 | Go/go-zero | 多平台SDK对接 |
| my-backend | 64 | Go/gRPC+HTTP | gRPC服务+物流平台B对接 |

如果全混在一个项目下，问答时检索噪音太大（APP端代码和后端代码混杂）。子项目实现了**二级隔离**。

### 3.2 存储结构

```
projects/{project}/
├── project.md              ← 项目简介（手动或自动生成）
├── raw/                    ← 项目级归档（兼容旧数据，无子项目时直接用）
├── wiki/
│   ├── sources/            ← 项目级源摘要（兼容旧数据）
│   └── sub-projects/       ← ★ 子项目目录 ★
│       └── {subName}/
│           ├── raw/        ← 子项目专属原始文件归档
│           └── wiki/
│               ├── sources/     ← 子项目源摘要
│               ├── entities/    ← 子项目实体
│               ├── concepts/    ← 子项目概念
│               ├── syntheses/   ← 子综合提炼
│               └── contradictions/ ← 子矛盾记录
```

### 3.3 FileSystem 的 Sub/SubSub 方法

```go
// storage/filesystem.go - 项目隔离的核心方法

func (fs *FileSystem) Sub(project string) *FileSystem {
    // 返回指向 projects/{project}/ 的新 FileSystem 实例
    // 所有 CRUD 操作自然路由到该目录
    return &FileSystem{
        Root: filepath.Join(fs.Root, "projects", project),
        // 继承其他配置...
    }
}

func (fs *FileSystem) SubSub(project, sub string) *FileSystem {
    // 返回指向 projects/{project}/sub-projects/{sub}/ 的实例
    // 用于子项目级别的操作
    return fs.Sub(project).SubRelative("sub-projects/" + sub)
}
```

**关键特性**：不改动任何现有方法的实现，只是换了 Root 路径。

### 3.4 引擎级联

```go
// engine.go - WithProject + WithSubProject

func (e *Engine) WithProject(name string) *Engine {
    return &Engine{
        LLM:      e.LLM,
        Storage:  e.Storage.Sub(name),          // → projects/{name}/
        Searcher: NewInMemorySearch(),
        Root:     filepath.Join(e.Root, "projects", name),
    }
    // 自动调 InitSearcher() 从项目的 sources/ 建索引
}

// API 层使用方式：
func handleQuery(query QueryRequest) {
    engine := globalEngine
    if query.Project != "" {
        engine = engine.WithProject(query.Project)
        if query.SubProject != "" {
            // 切换到子项目的 FileSystem 和搜索引擎
            engine.Storage = engine.Storage.SubSub(query.Project, query.SubProject)
            engine.InitSearcher()
        }
    }
    result := engine.Query(query.Question)
}
```

### 3.5 导入时的子项目路由

```
POST /api/ingest
Body: { raw_path: "...", project: "我的项目", sub_project: "my-service" }

↓ ingest.go 处理逻辑

if sub_project != "":
    rawFS = Storage.SubSub(project, sub_project)     // → sub-projects/my-service/raw/
    wikiFS = Storage.SubSub(project, sub_project)     // → sub-projects/my-service/wiki/
else:
    rawFS = Storage.Sub(project)                       // → projects/我的项目/raw/
    wikiFS = Storage.Sub(project)                      // → projects/我的项目/wiki/

→ 文件归档到对应的 raw/
→ LLM 分析后写入对应 wiki/sources/
→ 实体/概念写入 wiki/entities/, wiki/concepts/
→ 索引写入项目独立的 InMemorySearch
```

### 3.6 质量检查的子项目扫描

lintAll() 扫描范围覆盖所有层级：

```go
// lint.go - lintAll() 扫描流程

// lintCategory 返回值：(int, []LintIssue)
//   第一个返回值 = 扫描到的 .md 文件总数（无论是否有问题）
//   TotalPages 累加使用 pageCount（而非 issue 数量）
```

## 四、搜索系统（Search Engine）

### 3.1 架构

```
SearchEngine 接口（searcher.go）
├── InMemorySearch  ← 当前实现（纯内存倒排索引，零外部依赖）
└── ESSearch         ← 未来实现（只需实现 Index/Search/Remove 三个方法）
```

### 3.2 倒排索引原理

```
导入时建索引：
  文档 → 分块 → 分词(bigram + token) → 写入倒排表

  倒排表结构：
  map[string][]posting
  {
    "手机号": [{Source:"user_service.md", Title:"用户认证", Content:"..."}],
    "注册":   [{Source:"user_service.md", Title:"用户认证", Content:"..."}],
    "is_del": [{Source:"user_service.md", Title:"用户认证", Content:"..."}],
    ...
  }

查询时检索：
  关键词["手机号","唯一","注册"]
    → 查倒排表 O(1)
    → 合并所有匹配 posting
    → 按命中关键词数计分 (score = 匹配关键词数)
    → 排序取 Top10
    → 返回 scoredChunk 列表
```

### 3.3 分词策略

沿用 Bigram + Token 混合分词，与提问时的关键词提取逻辑完全一致：

- **空白 Token**：按空格切分，降为小写，去标点
- **中文 Bigram**：连续中文字符做二元组切分，如 "手机号唯一" → ["手机", "机号", "号唯", "唯一"]
- 同一文档内同一词只记一次（去重）

### 3.4 复杂度对比

| 操作 | 全遍历（旧） | 倒排索引（新） |
|------|-------------|---------------|
| 查询检索 | O(N × S) — N 文档数，S 文件大小 | O(K × M) — K 关键词数，M 命中块数 |
| 索引构建 | 无（查时现分块） | O(D × C) — D 文档数，C 块数（启动时一次性） |
| 新增文档 | 无需额外操作 | O(C) — 分块 + 分词 |
| 删除文档 | 无 | O(C) — 从倒排表逐词移除 |

### 3.5 索引生命周期

```
启动时：
  engine.InitSearcher()
    → 列出所有 sources/*.md
    → 逐个分块 → 分词 → 写入倒排表
    ≈ 36 页 100ms 内完成

导入新文档时：
  saveSourcePage() / saveCodeSourcePage()
    → e.indexSourcePage(slug)
    → getChunks() → Searcher.Index()

删除页面时：
  DeletePage() → Searcher.Remove(filePath)

项目级引擎创建时：
  engine.WithProject(name)
    → 新建 InMemorySearch
    → InitSearcher() 从项目的 sources/ 建索引
```

## 五、文件存储层（FileSystem）

### 4.1 目录结构

```
knowledge-base/
├── raw/                        ← 归档原始文档 (含 .hash 文件)
├── wiki/
│   ├── sources/                ← 源文档摘要页 (.md)
│   ├── entities/               ← 实体页
│   ├── concepts/               ← 概念页
│   ├── syntheses/              ← 综合提炼页
│   ├── contradictions/         ← 矛盾记录页
│   ├── history/                ← 历史快照
│   │   ├── raw/                ← 旧版归档文档
│   │   └── sources/            ← 旧版源摘要页
│   ├── index.md                ← 导航索引（自动维护）
│   └── log.md                  ← 演化日志
└── projects/                   ← 项目级隔离存储
    └── {项目名}/
        ├── project.md          ← 项目简介页
        ├── raw/                ← 项目专属归档
        └── wiki/
            └── {sources,entities,...}/
```

### 4.2 关键方法

| 方法 | 功能 |
|------|------|
| `NewFileSystem(root)` | 初始化目录结构（raw, wiki/sources, entities, concepts, syntheses, history） |
| `InitWiki()` | 首次创建 wiki/index.md 和 log.md |
| `ArchiveRaw(src)` / `ArchiveRawAs(src, name)` | 拷贝源文件到 raw/ 归档 |
| `WritePage(subdir, filename, content)` | 写入 wiki 页面，自动建目录 |
| `ReadPage(subdir, filename)` | 读取 wiki 页面 |
| `ListPages(subdir)` | 列出某类所有页面路径 |
| `SaveHash(filename, hash)` | 保存 SHA256 → raw/{name}.hash |
| `ReadHash(filename)` | 读取已存档哈希值 |
| `SaveHistoryRaw(name, content, ts)` | 保存旧版归档文件到 history/raw/ |
| `ReadArchivedRaw(name)` | 读取已归档的原始文件 |
| `Sub(project)` | **返回项目级 FileSystem 实例**，Root 指向 projects/{name}/ |
| `ListProjects()` | 列出 projects/ 下所有项目目录名 |

### 4.3 项目隔离

`Sub(project)` 是项目隔离的核心 —— 不改动任何现有方法的实现，只是换了一个 Root 路径。所有增删改查操作都自然地路由到项目目录下：

```go
fs := storage.NewFileSystem("knowledge-base")           // 全局
projFs := fs.Sub("我的项目")     // 指向 knowledge-base/projects/我的项目/
projFs.ListPages("sources")       // 列出 projects/我的项目/wiki/sources/
```

## 六、问答流程（Query Pipeline）

### 5.1 完整流程

```
用户输入问题
      │
      ▼
  extractKeywords(question)
      │
      ├─ 按空格分词 → token list
      ├─ 中文连续字符 → bigram 切分
      └─ 合并去重 → keywords[]
      │
      ▼
  Searcher.Search(keywords, 10)
      │
      ├─ 每个关键词去倒排表取 posting 列表
      ├─ 按 posting 合并计分（命中关键词数）
      ├─ 排序 → Top10
      └─ 返回 scoredChunk 列表
      │
      ▼
  buildContext(chunks, 6000)
      │
      └─ 拼接 Top10 块为上下文文本（≤6000 字符）
      │
      ▼
  generateAnswer(question, contextText)
      │
      └─ 构造 prompt → DeepSeek Chat API
         system: 基于以下知识库内容回答...
         context: Top10 块的摘要 + 来源标注
         → 返回回答文本
      │
      ▼
  提取引用源 → 返回 {answer, source_pages, confidence}
```

### 5.2 上下文构造策略

Top10 块按分数降序排列，逐一拼接到 context，超过 6000 字符自动截断。每个块的格式：

```
---
来源: {文件路径}
章节: {分块标题}

{分块内容}
```

### 5.3 项目级问答

请求中带 `"project":"我的项目"` 时，API Handler 调用 `engine.WithProject("我的项目")` 创建项目引擎。该引擎使用项目独立的 FileSystem（`projects/我的项目/`）和独立的 InMemorySearch（从项目的 sources/ 建索引），检索范围仅限该项目的文档。

## 七、质量检查（Lint System）

### 6.1 检查项

5 个并发 goroutine 扫描 5 类 wiki 页面（sources, entities, concepts, syntheses, contradictions），外加过期检测：

| 检查类型 | 严重级别 | 判断条件 |
|---------|---------|---------|
| 单字符名称 | error | 实体/概念名长度 ≤ 1 个 rune |
| **LLM 幻觉产物** | error | 实体/概念名未在任何引用源文档原文中出现 |
| 空壳页面 | warning/error | 正文去除标题后少于 1 行且有"待补充"占位符（≤400B 为 error） |
| 内容过少 | warning | 页面 < 250 字节 |
| 草稿 + 低置信度 | info | status=draft/空 && confidence=low/medium 且内容非空 |
| 源文档过期 | info | raw/ 文件哈希与已存档哈希不一致 |
| 综合提炼过期 | info | frontmatter 含 `stale: true` |

### 6.2 幻觉检测原理

```go
// 对 entities 和 concepts 页面：
1. 解析 YAML frontmatter 中的 sources 字段
2. 对每个引用源 → 找到其 source_file → 读 raw/ 下对应的归档文件原文
3. 在原文中全文搜索该实体/概念名称
4. 若未出现 → 标记为 "疑似 LLM 幻觉产物"
```

兜底策略：如果 raw/ 下所有归档文件内容都不含该名称，也判定为幻觉。

### 6.3 缓存与失效

- Lint 报告缓存 24 小时（`LintIfStale(24h)`），超时自动重新扫描
- `RefreshLint()` 强制刷新（质量检查页面的"开始检查"按钮）
- 删除页面后自动清空 lint 缓存（`invalidateCaches()`）

## 八、引擎核心（Engine）

### 7.1 结构

```go
type Engine struct {
    LLM      *llm.DeepSeekClient       // DeepSeek API 客户端
    Storage  *storage.FileSystem       // 文件存储
    Root     string                     // wiki 根目录
    Searcher SearchEngine               // 搜索引擎（倒排索引）

    lintMu        sync.Mutex           // lint 缓存锁
    lintCache     *LintReport          // lint 缓存
    lintCacheTime time.Time            // 缓存时间

    chunkMu    sync.RWMutex            // 分块缓存锁
    chunkCache map[string]chunkCacheEntry // 文件→分块缓存（mtime+size 校验）
}
```

### 7.2 分块缓存

`getChunks(path)` 维护基于文件 `mtime + size` 的缓存：

```
首次读取 → 读文件 → ChunkMarkdown() 分块 → 存入缓存
再次读取 → 检查 mtime+size 是否变 → 未变则直接返回缓存
文件变化 → 自动失效，重新分块
```

### 7.3 项目引擎

`WithProject(project)` 返回一个独立的 Engine 实例：

- 继承父引擎的 LLM 客户端
- 新的 FileSystem（Root 指向 projects/{project}/）
- 新的 InMemorySearch（从项目 sources 建索引）
- 启动时自动调 `InitSearcher()`

## 十、启动与关闭

### 9.1 启动流程

```
1. 读取 DEEPSEEK_API_KEY（环境变量 或 .env 文件）
2. NewFileSystem(wikiRoot) → 创建目录结构
3. InitWiki() → 首次创建 index.md + log.md
4. NewDeepSeekClient() → 初始化 API 客户端
5. NewEngine() → 组装 Engine（含 InMemorySearch）
6. InitSearcher() → 从磁盘全量构建搜索索引
7. net.DialTimeout 检测端口 → 占用则自动 kill 旧进程
8. http.Server.ListenAndServe() → 启动服务
9. signal.Notify(SIGINT, SIGTERM) → 等待信号
```

### 9.2 优雅关闭

```
收到 SIGINT/SIGTERM
    → 打印 "正在关闭服务..."
    → srv.Shutdown(ctx)  等待 10s 超时
    → 打印 "服务已安全关闭"
    → 退出
```

区别于之前的 `http.ListenAndServe` 直接阻塞 + `log.Fatal` 退出，现在的实现允许在关闭时等待正在处理的 HTTP 请求完成。

## 十二、代码分类系统（classify.go）

### 12.1 设计原则

**100% 路径规则，零 LLM 调用。** 分类在导入时自动完成，不增加 API 成本。LLM 接收分类信息作为上下文，写出更准确的摘要。

### 12.2 三层分类体系

| 维度 | 含义 | 示例值 | 来源 |
|---|---|---|---|
| `layer` | 技术层级 | handler, service, model, repository, sdk, callback | 目录路径 |
| `domain` | 业务域 | 订单, 配送, 门店, 电商平台A, 物流平台B | 路径+文件名关键词 |
| `kind` | 代码类型 | API入口, 业务逻辑, 数据模型, 外部平台适配 | layer 映射 |

### 12.3 层级分类规则

```go
var layerRules = []layerRule{
    {[]string{"handler", "controller", "api"}, "handler"},
    {[]string{"service", "logic", "biz", "usecase"}, "service"},
    {[]string{"model", "entity", "schema", "domain"}, "model"},
    {[]string{"repo", "repository", "dao", "mapper"}, "repository"},
    {[]string{"sdk", "client", "adapter", "platform"}, "sdk"},
    {[]string{"callback", "notify", "webhook"}, "callback"},
    {[]string{"job", "cron", "task", "schedule"}, "job"},
    {[]string{"page", "pages", "view", "views"}, "page"},
    {[]string{"component", "components", "widget"}, "component"},
    // ...
}
```

匹配逻辑：路径段包含关键词（如 `/handler/`、`handler/`、`/sdks/` → 匹配 `sdk`）。

### 12.4 业务域分类规则

```go
var domainRules = []domainRule{
    // 优先级：外部平台名 > 业务域 > 通用概念
    {[]string{"dada", "电商平台A"}, "电商平台A"},
    {[]string{"haohuisong", "物流平台B", "hhs"}, "物流平台B"},
    {[]string{"order", "订单"}, "订单"},
    {[]string{"delivery", "distribution", "配送", "运力"}, "配送"},
    {[]string{"payment", "pay", "refund", "支付", "退款"}, "支付"},
    // ...
}
```

匹配逻辑：按规则优先级顺序遍历，先路径段精确匹配，再文件名模糊匹配。

## 十四、导入前置校验（validate.go）

### 14.1 三重检查

`ValidateImport(rawPath)` 在导入前执行只读检查：

| 检查 | 内容 | 技术 |
|---|---|---|
| Check A | 哈希匹配：统计 new/changed/unchanged 文件数 | SHA256 + raw/.hash 对比 |
| Check B | 跨项目碰撞：检测特征文件是否在其他子项目归档 | 入口文件扫描 + 兄弟 raw/ 比对 |
| Check C | 路径合理性：路径存在、非噪声目录、文件数、项目结构 | 文件遍历 + 目录名校验 |

### 14.2 API 端点

- `POST /api/ingest/validate` — 纯只读预检，返回 `ValidationReport`
- `POST /api/ingest` — 自动跑校验，结果附在响应的 `validation` 字段

### 14.3 过滤规则统一

`collectImportableFiles` 复用 `isNoiseCodeFile` 和 `isNoiseDirName`，确保校验和实际导入统计一致。所有噪声目录名集中在 `noiseDirNames` map 中统一管理。

## 十六、数据流总结

```
导入方向（写时）：
  原始文件 (指定 project + sub_project)
    │
    ├─ [路由] SubSub(project, sub) → 定位到 projects/{p}/sub-projects/{sp}/
    │
    ├─ LLM 提取元数据 → 源摘要页 (sub-projects/{sp}/wiki/sources/)
    ├─ LLM 提取实体/概念 → 累积合并页 (entities/, concepts/)
    ├─ 分块 → 分词 → 项目独立的倒排索引 (InMemorySearch)
    └─ SHA256 哈希 → raw/ + {name}.hash → 增量更新检测

查询方向（读时）：
  用户问题 (+ 可选 project + sub_project)
    │
    ├─ [路由] WithProject(p).WithSub(sp) → 切换到子项目引擎
    │         → 子项目 FileSystem + 子项目 Searcher
    │
    ├─ 分词 (bigram + token) → 关键词列表
    ├─ 查子项目倒排索引 → Top10 块（O(K×M) 时间复杂度）
    ├─ 构建上下文（≤6000 字符，仅含子项目内文档）
    └─ DeepSeek Chat API → 生成回答
       → 返回 {answer, source_pages, confidence}
```

## 十七、后期切 ES 过渡方案

当前搜索接口已抽象为 `SearchEngine` 接口：

```go
type SearchEngine interface {
    Index(docPath string, chunks []storage.Chunk)
    Search(keywords []string, topN int) []scoredChunk
    Remove(docPath string)
    Rebuild(listPages, getChunks) error
}
```

将来换 Elasticsearch 时：

1. 新建 `searcher_es.go`，实现 `ESSearcher` 结构体
2. `Index()` → ES Bulk API 写入
3. `Search()` → ES Search API 查询（BM25 或自定义评分）
4. `Remove()` → ES Delete API
5. `NewEngine()` 里改一行：`Searcher: NewESSearcher("http://localhost:9200")`
6. `go.mod` 加 ES 客户端库依赖

`query.go`、`ingest.go`、`lint.go` 无需任何改动。
